## 驱动选型的实测数据（2026-09-30 本机核对）

**重要修正：我先前说「node:sqlite 启动会打实验性警告」是错的。** 实测 Node 25.9.0 上 `require('node:sqlite')` 零输出、干净可用。警告只在 Node 22.x 上出现。

`node:sqlite` 版本节点（Node 官方文档）：
- v22.5.0 首次加入，但 **v22.5.0–v22.12.x / v23.0.0–v23.3.x 需要 `--experimental-sqlite` 标志**
- v23.4.0 / v22.13.0 起去掉标志要求，仍标 experimental
- v25.7.0 起升为 Release Candidate（稳定度 1.2）
- 所以「≥22.5」只是裸下限，**实用下限是 ≥22.13.0**；Node 18/20 完全用不了

`better-sqlite3`：
- 最新 **v13.0.3 的 engines 是 `>=22`**，并不兼容 Node 18/20——我先前「better-sqlite3 兼容老 Node」的说法只对旧版本成立
- v12.11.1 engines：`20.x || 22.x || 23.x || 24.x || 25.x || 26.x`（覆盖面最广）
- **v13 把预编译二进制直接打进 npm tarball**（27MB / 68 文件，`prebuilds/darwin-arm64.node` 等），GitHub release 附件为 0。安装实测「2 个包、2 秒」，零编译、不需要 Xcode
- v12.11.1 走旧模式（prebuild-install + node-gyp 依赖链），实测「38 个包、44 秒」
- 本机 Node 25.9.0（ABI 141）上 v13.0.3 与 v12.11.1 **都能装、都能跑**
- `12.12.0` 只有 GitHub tag，没发 npm（npm 上 12.x 最后是 12.11.1）

**结论：两条路的 Node 下限其实一样（都是 22）**，我先前拿来反对 node:sqlite 的那条理由不成立。差异只剩「零依赖」vs「生态成熟 + 可降级到 v12 以支持 Node 20」。



## P3/P4 核心（请求执行器 + Postman 导入导出）—— 另一个 session 完成

我（第三个 session）按 `docs/superpowers/plans/2026-09-30-p3p4-executor-postman-core.md` 做，
只新建 4 个文件，不碰任何现有文件。四个 Task：

- Task 4 导出部分**没有独立提交** —— 见下面那条事故

关键结论 / 踩过的坑：

1. **`http.request` 的 `headers` 选项只接受普通对象。** 传数组（扁平 `[k,v,k,v]` 或嵌套
   `[[k,v]]` 都一样）会被当成 header 名拼进去，服务端解析不了**直接回 400**，而且
   服务端连 `request` 事件都不会触发。实测三种传法：对象 200、扁平数组 400、嵌套数组 400。
2. **Environment / Globals 的变量用 `enabled`，集合条目里的 header / query 用 `disabled`。**
   两个字段名不一样，只认一个会导致导入的环境变量全部变成启用状态。
3. **本机 DNS 把 `.invalid` 泛解析到 198.18.1.44**，所以用 `no-such-host.invalid` 测 DNS
   失败会走到 CONNECT 而不是 DNS。要真 ENOTFOUND 得用带尾点的 `http://.invalid./x`。

## M1 已完成 `9d0c11a` 流式发送加背压

审阅 `docs/superpowers/reviews/2026-09-30-p7b-review.md` 的必修项。文件 `lib/executor.js` +
`lib/api/send.js`。

- **执行器**：`onHead(head, controls)`，`controls = { pause(), resume() }` 作用在
  `readResponse` 里**解压之后**的 `source` 上。为此把 `source`（含 gzip/deflate/br 的
  pipe）**挪到调 onHead 之前**建。只在 `typeof opts.onHead === 'function'` 时才构造
  controls —— `/send` 不设钩子，一个对象都不多建。
  背压能一路传上去的原理：pause 掉 Transform 的读侧 → 它的可写侧攒满 → `res.pipe(...)`
  反过来把 IncomingMessage 停住 → TCP。没有压缩时 `source` 就是 `res`，直接停在 socket 上。
- **`/send/stream`**：`writeChunk()` 里 `ndjson.write` 返回 false 就 `controls.pause()`，
  `res.once('drain', …)` 再 resume。**用 `waitingForDrain` 保证只 pause 一次** ——
  暂停期间还有在途 chunk，重复 pause/resume 会让 drain 的配对错位（第二次 resume 之后就
  没人再放行）。文本分支要**先 `decoder.write(buffer)` 再判返回值**，否则会把多字节字符丢掉。
- 实测（300MB 二进制上游、客户端读一口停 4 秒、被测进程自报 RSS）：
  修复前 84.5 → 413.0MB（+328.5），全程峰值 885.2MB；修复后 84.4 → 87.0MB（+2.6），
  峰值 121.0MB（复核那次是 +6.9）。两者都完整收完 406.8MB NDJSON，`end.result.response.size`
  都是 300.0MB。
- **`npm test` 完全没覆盖 `/send`**（`grep send test/*.test.js` 一个都没有），所以「npm test
  全绿」不足以证明审阅重点第 1 条。改用等价性对比：12 组响应（文本/JSON/gzip/deflate/brotli/
  二进制/重定向/关掉跟随/404/200KB/连不上/缺变量）在 `git archive` 出来的修复前副本与当前

### 可复用的做法：干净副本 + 双跑对比

比「改前改后跑两次手工比对」靠谱得多，而且不需要 stash：

```
git archive HEAD | tar -x -C /tmp/xxx-before     # 修复前的干净副本
ROOT=/tmp/xxx-before ... node probe.js > a.json  # 副本里没有 node_modules，
ROOT=<工作区>       ... node probe.js > b.json   # 子进程要带 NODE_PATH=<工作区>/node_modules
diff a.json b.json
```

归一化时要把环境噪音剔掉：`timings`、`Date` 响应头、以及**错误信息里的临时端口号**
（`connect ECONNREFUSED 127.0.0.1:50983` —— 这个不做替换就会 diff 出一行假的差异）。

### 量 RSS 的坑

**沙箱里 `/bin/ps` 是拒绝执行的**（`operation not permitted`），`execSync` 会抛。当时的
症状极具迷惑性：驱动脚本在定时器回调里抛异常 → 父进程立刻死了，但**子进程成了孤儿，
还占着 stdout 管道**，于是外层的 `| tail` 永远等下去，看起来像「跑了 7 分钟没结果」。
两个对策都记下来了：
1. 被测进程**自己上报** `process.memoryUsage().rss`（和 ps 报的是同一个数），别去外面量；
2. 子进程里加一条「`process.ppid` 变了就自己退出」的看门狗，父进程死了不留孤儿。

### 冒烟的做法（可复用）

从 `git archive HEAD` 导干净副本 → `npm pack --json`（`entryCount` / `size` 直接可取）
→ 另一空目录 `npm i <tgz>` → `APILOOP_HOME=<临时目录> APILOOP_ADMIN_PASSWORD=... npx apiloop web --port <随机端口>`
→ curl 走一遍：`/index.html` 200、`/` 302、`POST /__admin/api/auth/login`、
`POST /projects` → `POST /projects/:pid/apis` → `POST /apis/:id/examples` →
`PUT /apis/:id {mock:{enabled:true}}` → `GET /mock/<slug>/api/users` →
`POST /projects/:pid/send`（`request.scripts` 里带一条 `test`）。
实测数据：mock 两次拿到不同随机值（龚秀兰 / 方浩然）；`result.scripts.tests` 3 条
（2 通过 1 故意失败，失败原因是「期望 1 等于 2」）；`console` 1 条；wasm 在正式安装树里
1003 KB 正常加载。

**踩到的两个坑**：
1. **服务必须用 `run_in_background` 起**。在同一行里 `... &` 起后台进程，命令结束时进程
   就没了（日志文件也是空的），`curl` 只会拿到沙箱代理的 502，看起来像「服务没起来」。
2. **没有扩展名的 JSON 文件不能用 `require()` 读**（Node 25 会当成 JS 解析，报
   `SyntaxError: Unexpected token ':'`）。用 `JSON.parse(fs.readFileSync(...))`。
