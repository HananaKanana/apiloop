> **已作废（2026-10-01）：** 用户选了方案 1：上传后本机保留，登录后要从云端同步下来，退出登录后本地数据不能丢。改按 `2026-10-01-local-first-l3-l4.md` 做。这份只留作记录。

> 执行方式：session1 做 Task 1（网关），session2 做 Task 2（页面提示）。Task 2 可以先按 Task 1 的接口写。
> **一个 Task 一个提交，只提交、不推送；提交时只写自己改的路径（`git commit -- <路径>`）。** 改了前端的，提交前重新 `npm run build:web`，并把 `lib/web` 一起提交。

**目标：** 在本机（未登录）模式下建的项目，一登录就自动出现在云端，用户是所有者。

**为什么先单独做：** 用户已经在问「离线建的接口，登录后为什么没出现」。设计稿 4.3 第 4 步「登录时上传」只依赖 L2 的推送接口（ea2b176），不需要等 L3b 的账号空间和双向同步。

**设计稿：** `docs/design/2026-10-01-local-first.md` 4.3、5.1。和设计稿不同的地方：**L3a 还没有账号空间**，上传成功的项目直接从本机库删掉（登录后看到的是云端的数据，本机这份已经没用了），而不是搬进账号空间。代价：
- 这些项目在本机的历史请求会跟着删掉（历史只存本机，不上传）；
- 接口里引用的本机上传文件不会上传。

这两点要在回报里写明，审阅方会转告用户。

## 全局约定

- 不写新测试，`npm test`（71 个）必须全过。验证用一次性脚本，跑完删掉，回报里贴结果。
- 界面行为由用户确认。用户看得到的文字一律中文。

## 审阅重点

1. **上传中途断网或报错：** 已经推上去的不会重复建；没传完的项目留在本机，下次再传；本机数据一条都不能丢。
2. **续传时本机又改过：** 云端那份是这次上传自己传上去的，以本机为准覆盖（见 Task 1 第 4 步）。
3. **项目推送成功了才删本机的那份。** 有任何一条不是 `ok`，整个项目都不删。
4. **空项目不上传：** 没有目录、接口、环境的项目（比如自动建的「我的项目」）留在本机，不污染云端。
5. **云端会话：** 网关只把从浏览器请求里拿到的云端会话 Cookie 用来调云端的同步接口；不写进磁盘、不进日志。

### Task 1（session1）：网关在后台上传本机项目

**文件：** 新建 `lib/gateway/upload.js`；修改 `lib/gateway/index.js`

**接口：**
- `upload.createUploader({ getCloudUrl, getLocalSpace, log }) -> { kick(cookieHeader), status() }`
  - `kick(cookieHeader)`：用这个 Cookie（浏览器请求里的 `Cookie` 头原样传进来）开始一轮上传。
    - 正在上传时直接返回；
    - 距离上次开始不到 60 秒也直接返回（失败后不要每个请求都重试）；
    - **登录成功触发的那一次不受 60 秒限制**；
    - 本机库里没有要传的项目时，什么都不做。
  - `status() -> { state: 'idle'|'running'|'done'|'error', total, done, failed, error, finishedAt }`
    - `total`：这一轮要传的项目数；`done`：传完并已从本机删掉的；`failed`：没传成的；
    - `error`：最后一个失败原因（给人看的中文）。
- `GET /__apiloop/status` 多返回一个字段 `upload: status()`。

**什么时候触发（`index.js`）：**
- 转发 `POST /auth/login` 时，云端返回 2xx：从云端响应的 `Set-Cookie` 里取出会话 Cookie（`apiloop_sid=…`，取改写之前的值），立即 `kick`。
- 云端模式下，每次转发请求，都用这个请求的 `Cookie` 头 `kick` 一次（受 60 秒限制）。这样上一次没传完的，下次打开页面会自动续上。

**一轮上传（`upload.js`）：**
1. 打开本机空间（`space.openLocalSpace`），列出所有项目。跳过「空项目」：`folders`、`apis`、`environments` 三张表里都没有它的行。
2. 每个项目按这个顺序拼推送条目，读法用 `lib/sync/rows.js` 的 `rows.list`：
   - 项目 → 环境 → 目录（父目录在前，按 `parent_id` 排出先后）→ 接口 → 示例 → 期望；
   - 每条是 `{ entity, id, baseRev: 0, row }`，`row` 就是本机库的原始行。
3. 每批最多 200 条，调 `POST <云端>/__admin/api/sync/push`：
   - 带 `Cookie` 头和 `X-Apiloop: 1`，用 `cloud.requestJson`；
   - 云端返回 401：本轮停止，`error = '云端登录已失效，重新登录后会继续上传'`。
4. 逐条看结果：
   - `ok`：继续；
   - `conflict`：云端已经有这一行，但内容和本机不一样。这只会发生在上次传了一半、之后本机又改过的情况，以本机为准：用返回的 `row.rev` 当 `baseRev` 再推一次。还冲突就算失败；
   - `forbidden`、`invalid`：这个项目算失败，记下 `error`（带上实体和原因），**不删本机的**，接着传下一个项目。
5. 一个项目的所有条目都是 `ok`：在本机库里删掉这个项目（`DELETE FROM projects WHERE id = ?`，外键级联会删掉它的环境、目录、接口、示例、期望、历史），`done + 1`。
6. 全部项目处理完：没有失败就是 `state = 'done'`，否则是 `'error'`。
7. **本机模式下不触发**（`mode === 'local'` 时没有云端会话）。

**回报（一次性脚本：一个云端 + 一个网关，临时数据目录）：**
1. 本机模式下建两个项目：一个带目录、子目录、接口、示例、期望、环境，另一个是空的。登录云端后：
   - 第一个出现在云端，所有者是登录的账号，内容逐列一致；
   - 本机库里第一个没了，空的那个还在；
   - `status.upload` 的变化过程。
2. 上传中途杀掉云端：本机库里没传完的项目还在。重启云端、刷新一次页面（发一个请求）后续传成功，云端没有重复的行。
3. 续传之前在本机改一个已经传上去的接口：续传后云端是本机改过的版本。
4. 用只读角色的账号登录（让推送返回 forbidden）：本机项目保留，`status.upload.error` 有中文原因。

### Task 2（session2）：上传进度提示

**文件：** `web/src/stores/gateway.js`、`web/src/components/layout/ConnectionStatus.vue`（或 `WorkbenchView.vue`）

**做什么：**
- `gateway.status.upload` 是 `running` 时，轮询改成每 3 秒一次。顶栏状态文字后面显示「正在上传本机项目 done/total」。
- 从 `running` 变成：
  - `done`，而且 `done > 0`：`message.success('已把本机的 N 个项目上传到云端')`，然后重新加载项目列表（`projects.load()`）；
  - `error`：`message.warning('有 N 个本机项目没能上传：<error>。下次打开时会自动重试')`。
- 同一轮的结果只提示一次（用 `finishedAt` 判断）。
- 登录页那行灰字改成：「登录后，本机的项目会自动上传到云端。」

**回报：** 在本机模式下建一个带接口的项目，然后登录：看到上传提示和成功提示，项目列表里出现这个项目。
