## 必修

### M1. `/send/stream` 没有背压：浏览器读得慢，服务端就会把整个响应体堆在内存里

- **实测**：上游以最快的速度推送 300MB 的二进制数据，客户端读了一口就停下。4 秒之后，服务端进程的 RSS 从 **83MB 涨到了 568MB**。这里面包括 300MB 的原始数据，加上 base64 和 JSON 带来的膨胀。
- **影响**：部署在远端时，浏览器到服务端的带宽，往往远小于服务端到目标接口的带宽。只要下载一个几百 MB 的文件，就可能把容器的内存撑爆。`/send` 有 `maxBodyBytes` 兜底，流式接口「全部转发」却没有任何上限。
- **根源在我**：计划里写了「`chunk` 全部转发」，却没写背压要求。
- **修法**：
  - 执行器：`onHead(head, controls)` 多传一个参数 `controls: { pause(), resume() }`，作用在 `readResponse` 里的 `source` 上（解压后的流，或者原始的 `res`）。不设置流式钩子时，不会传这个参数，`/send` 的行为不变。
  - `/send/stream`：`onChunk` 里的 `ndjson.write` 返回 false 时，调用 `controls.pause()`，然后 `res.once('drain', controls.resume)`。
  - 暂停期间不会触发超时，因为 `head` 到达之后总超时的计时器已经清掉了；取消照常通过 AbortController 处理。
- **自测**：把我上面那个场景重跑一遍，也就是 300MB 的上游、客户端读一口就停。RSS 的增长应该在几十 MB 以内。客户端恢复读取之后，数据要能完整读完，`end` 事件里的 `size` 等于 300MB。

## 小瑕疵（不强制）

- **N1**：WebSocket 的 `/events` 连接同样没有背压。但事件来自一个有上限的缓冲区（500 条，每条最大 64KB），上游一直高速推送的场景也比较少见，所以不强制处理。如果顺手改的话，可以在 `write` 返回 false 时丢掉 `text` 和 `base64` 字段，只推送 `size`，并标记 `dropped: true`。前端之后可以通过 `after` 重新拉取缓冲区里的完整内容。
