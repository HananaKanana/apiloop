## 总体评价

质量高，审阅重点第 1、2、3、5 条基本都通过：

- **Cookie 边界**：
  - 跨站设置 Domain、只有一段的 Domain（`com` / `.com` / `localhost`）、IP 地址被伪装成后缀，都会被拒绝；
  - host-only 的 cookie 不会发给子域或父域；
  - `Domain=x.com` 不会匹配到 `evilx.com`；
  - `Secure` 的 cookie 不会走 http；
  - `Path=/api` 的 cookie 不会发给 `/apix`；
  - 过期的 cookie 不发送；`Max-Age` 优先于 `Expires`；`Max-Age=0` 会删除 cookie；
  - default-path 的推导正确；
  - `maskSetCookie` 正确。
- **重定向**：登录接口返回 302 并带 `Set-Cookie`，跳转后的 `/me` 请求带上了 `sid`；用户手写的 `Cookie` 优先。
- **代理**：
  - http 目标会把请求以绝对地址发给代理，代理地址里经过 URL 编码的密码被正确解码成 `Proxy-Authorization`；
  - https 目标通过 CONNECT 访问成功，`rejectUnauthorized: true` 时照样会拒绝自签名证书（返回 TLS 错误）；
  - `noProxy` 命中时直连，代理没有被调用；
  - 代理端口没有监听时返回 `PROXY` 错误；
  - 所有返回结果和错误信息里，代理密码都已打码。
- **用户隔离**：bob 的请求不会带上 alice 的 cookie；bob 看不到 alice 的 cookie，删除 alice 的 cookie 返回 404。
- **代理设置**：
  - 普通用户修改代理返回 403；设置 `socks5://` 地址返回 400；
  - GET 接口返回的密码打码；
  - 提交 `***` 时，库里保留原来的密码。
- **历史对执行结果打码**：`result.request.headers` 里 jar 自动补上的 `Cookie`、手写的 `Authorization` 都已经是 `***`；`Set-Cookie` 的值也打了码。

## 必修

### M1. 历史里的原始请求 `request.spec` 把凭据明文暴露给了项目其他成员

- **实测**：alice 发送的请求里，手写了请求头 `Authorization: Bearer TOK`，同时设置了 `auth: { type: 'bearer', token: 'AUTHTOK' }`。bob（同项目 editor）调用 `GET /history/:id` 时，在 `request.spec.params.headers` 和 `request.spec.auth` 里都能看到明文的 `TOK` 和 `AUTHTOK`。
- **原因**：契约第 12 节只要求对 `result` 打码，漏掉了 `spec`。**这是我写契约时的疏漏，不是你的实现问题。**契约现在已经修订，见第 12 节新增的「历史中的原始请求也要打码」。
- **修法**：
  - 按修订后的契约，写库时 `spec` **不做任何处理**，原样保存，因为发起人自己重放时需要完整内容。
  - 只在 `GET /history/:id` 返回之前判断：如果 `entry.userId !== req.user.id`，就对**副本**做打码。
  - 打码函数放在 `lib/cookies.js` 或新建的 `lib/redact.js` 里，函数名为 `redactRequestSpec(spec)`。
- **自测**：
  - alice 查看自己的这条历史，能看到明文；
  - bob 和 admin 查看时，这两处都显示 `***`；
  - 响应体里的内容不做处理，因为服务端回显什么我们管不了，这个限制写进 README 的一句话说明里。

## 建议修

### S1. 按 RFC 6265bis，拒绝从 http 响应设置 `Secure` cookie，也不允许用非安全 cookie 覆盖已有的 Secure cookie

- **实测**：`parseSetCookie('a=1; Secure', 'http://x.com/')` 现在会被接受。
- **风险**：在 http 链路上的中间人，可以借此注入一个只会在 https 请求里发送的 cookie（会话固定）。
- **修法**，两条规则：
  1. 请求 URL 是 http 时，带 `Secure` 属性的 `Set-Cookie` 一律拒绝；
  2. 请求 URL 是 http 时，如果 jar 里已经有同名、并且 domain 可以互相匹配的 Secure cookie，这次的非安全 cookie 不允许覆盖它。
- 这两条都是现代浏览器的通行做法。计划原本只要求按 RFC 6265 实现，所以这一条不算你违反计划，但值得补上。

- 只提交你自己改的文件。
- 回报时附上 M1 自测的三种身份（alice 本人、bob、admin）分别看到的结果。

## 必修

### M2. apikey 鉴权的 key，会以明文写进项目成员都能看到的历史

- **实测**：直接调用 `executor.execute`，传入 `auth: { type: 'apikey', key: 'X-Api-Key', value: 'SECRET123', in }`：
  - `in: 'header'`：`result.request.headers` 里是 `["X-Api-Key","SECRET123"]`；
  - `in: 'query'`：`result.request.url` 是 `http://…/x?X-Api-Key=SECRET123`。
- **原因**：
  - `forHistory` 只对固定的三种请求头打码（Cookie、Authorization、Proxy-Authorization）。apikey 的请求头名字是用户自己定的，放在 query 里时则会拼进 URL，这两种情况都会原样写进历史。
  - M1 修好之后，bob 看到的 `spec.auth.value` 已经是 `***`，但同一条历史的 `result` 里还是明文。**这仍然是契约的疏漏**：第 12 节只列了三种固定的请求头。契约已经修订，见第 12 节「历史记录要打码」下面新增的第三条。
- **修法**：
  - `forHistory(result)` 改成 `forHistory(result, auth)`，`auth` 传入**变量替换之后**的鉴权，也就是 `variables.resolveSpec(spec, vars).spec.auth`（`vars` 在同一个作用域里已经有了）。因为 `spec.auth.key` 和 `value` 可能写的是 `{{apiKey}}`，而执行器实际使用的是替换之后的值。
  - `in: 'header'`：把 `auth.key` 这个名字（不区分大小写）也加进本次要打码的请求头名单。
  - `in: 'query'`：执行器是在 URL 末尾追加 `encodeQueryPart(key) + '=' + encodeQueryPart(value)`。按同样的方式编码出这一段，只替换**最后一次出现**的那一段，把值换成 `***`。不要用 `new URL` 整体重新拼接，否则 URL 其余部分的编码可能被改掉。
  - `key` 为空时不处理，执行器本来也不会加。
  - 发给发送者本人的 `result` 保持原样，这一点不变。
- **自测**：header 和 query 两种方式各发一次，并且 `key` 和 `value` 都用环境变量来写。调用 `GET /history/:id` 查看，`result.request` 里不应该出现明文的 value；`/send` 直接返回给发送者的结果里，应该仍然是明文。

## 建议修

### S2. 修改代理地址时保留 `***`，旧密码会被带到新地址

- **实测**：直接调用 `proxy-settings` 模块：
  1. 先 `set({ http: 'http://u:TOPSECRET@corp-proxy:3128' })`；
  2. 再 `set({ http: 'http://u:***@attacker.example:8080' })`；
  3. 库里存的变成了 `http://u:TOPSECRET@attacker.example:8080`。
- **风险**：
  - **误操作**：admin 换了一台代理，却忘了改密码那一段，原来那台代理的密码就会发给新代理。
  - **绕过打码**：打码本来就是为了连 admin 也看不到明文密码，但现在只要把主机改成自己的机器，就能在代理日志里收到明文密码。
- **原因**：`restorePassword`（`lib/proxy-settings.js:128`）只要看到 `:***@` 就把旧密码填回去，不检查地址的其他部分是否也变了。
- **修法**：
  - `incoming` 和 `previous` 解析后，比较协议、主机、端口、用户名，四项都相同时才填回旧密码；
  - 只要有一项不同，就返回 400：「代理地址变了，请重新输入密码」；
  - 契约第 12 节 `PUT /settings/proxy` 那一行已经按这条规则修订。
