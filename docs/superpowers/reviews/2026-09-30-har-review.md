# HAR 导入审阅意见（661f6a5、017aa3e）

> 本轮审代码，并在最小的 fake 环境里实际运行。**界面没有用浏览器验证**，界面相关的结论都是按代码推演得出的，需要用户按计划里的清单手工确认。

## 总体评价

**解析器写得扎实**，逐条对照审阅重点：

1. **凭据**：请求头名一律转成小写后比对；`Cookie`、`Authorization`、`Proxy-Authorization`、`Set-Cookie` 都会去掉。HAR 里的 `request.cookies` 和 `response.cookies` 两个数组根本没有读进来，URL 用的是 `origin + pathname`，所以地址里的 userinfo 也不会带进来。
2. **性能**：3600 条记录、29.6MB 的文件，预览 444ms，导入 774ms。去重时先判断是否已达上限，再计算指纹，避免给超出上限的响应体白白算指纹、占内存。
3. **残缺数据**：`headers` 为 null、`postData` 没有 `text`、`content` 缺失、`startedDateTime` 无效、地址解析不了，这些情况都覆盖到了。排序时先把时间有效和无效的分成两组，保证了稳定性，不依赖引擎的排序实现。
4. **合并的键**：`方法 + origin + pathname`。不同主机上的相同路径，会分进两个不同的主机目录。
5. **权限**：`resolveTargetProject` 是从 Postman 导入原样抽出来的，抽取之后 Postman 导入的行为没有变化，`npm test` 71/71。

**前端**：
- 超过 50MB 在前端就拦下，不发请求；
- 「保留凭据」的勾选状态一改，就重新预览；
- 这个选项的后果用警告色写出来了；
- viewer 只能选择「新建项目」。

## 必修

### M1. 选中大文件后，整段 HAR 文本被绑定进了文本框

- **位置**：`web/src/components/importExport/ImportDialog.vue` 第 218 行和第 458 行。选择文件后执行 `harText.value = await readFileAsText(file)`，而同一个 `harText` 又用 `v-model` 绑定在带 `autosize` 的 `n-input type="textarea"` 上。
- **推演**：选中一个 30MB 的 HAR 之后，浏览器要把 30MB 的文本塞进 textarea。naive-ui 的 `autosize` 还会把同样的内容复制到一个隐藏的元素里，用来测量高度。这一步大概率会让页面卡住好几秒，甚至崩溃。这正是审阅重点第 2 条要防止的情况。你的性能数字测的是服务端，没有覆盖到这一段。
- **修法**：
  - 文件内容放在一个**不参与渲染**的变量里，比如普通的 `let harFileText`，或者 `shallowRef`；
  - 选中文件之后，**隐藏文本框**，只显示「文件名（大小）」和一个「清除」按钮；
  - 文本框只用来粘贴，发送时取「文件内容或者粘贴的内容」其中之一；
  - 顺手检查一下 Postman 页签有没有同样的写法。Postman 文件通常很小，所以不强制改，但如果写法相同，一起改掉最好。

## 建议修

### S1. 50MB 的请求体在登录校验之前就被解析了（根源是我的计划）

- **实测**：用干净副本启动服务，**不登录**，直接往 `/import/har` 发送 40MB 的 JSON。服务端先完整解析，再返回 401；同样的请求发到 `/import/postman`，会被 4MB 的上限直接拒绝。
- **原因**：计划里要求把 50MB 的解析器挂在「全局 4MB 解析器之前」，而全局解析器本身就在 `requireLogin` 之前。这是我写计划时没有考虑到的。
- **影响**：任何能访问到这个端口的人，都能让服务端缓冲并解析 50MB 的数据。Docker 部署时，服务默认对局域网开放。
- **修法**：
  1. 全局的 4MB 解析器对 `/import/har` 开头的路径直接跳过，比如包一层 `function (req, res, next) { if (req.path.indexOf('/import/har') === 0) return next(); json4mb(req, res, next); }`；
  2. 50MB 的解析器挂到 `api.use(auth.requireLogin)` **之后**、`harApi` 路由之前。

  这样，没登录的请求在读取请求体之前就会被拒绝。

## 小瑕疵（不强制）

- **N1**：`postData.params` 里如果有 `null` 这样的项，`toFormRow(item)` 会抛出异常。路由会把它转成 400，所以不会 500，但结果是**整次导入失败**，而且错误信息是英文的 `Cannot read properties of null`，违背了「能导入的照常导入」。建议在 `toBody` 里先把非对象的项过滤掉。
- **N2**：示例的响应体是原样保存的。登录接口的响应体里常常就有 token，比如 `{"token":"…"}`，契约没有要求处理这种情况。**我不要求你改代码**，但在交给文档的说明里要写清楚这一点，让用户知道导入前需要自己检查。
