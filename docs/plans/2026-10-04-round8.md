写于 2026-10-04。主会话写，session1 / session2 照着做。用户要求先开发、最后统一测试，验收清单最后统一整理。

开工前先读 `CLAUDE.md`、`docs/HANDOFF.md`、`docs/plans/2026-10-03-round3.md` 第 0 节（规矩一样）。

**背景：** 用户团队有类似 Jenkins 的自动化工具，接口大多在内网。这一轮先把「测试集」和「压测」在客户端里做出来；

云端（Docker）默认 `SERVER_SEND=0`，不替网页版发请求。测试集运行、压测都**在本机网关上跑**；网页版点运行时提示去装客户端。

## 1. 测试集（session2）

### 要解决的问题

现在的「批量运行」只能跑一个目录、按目录顺序、每次重新勾选，跑完结果就没了。用户要的是：

- 从不同目录里挑几个接口**排成一个流程**（登录 → 建订单 → 查订单 → 取消订单），存下来反复跑；
- 同一个流程**换一批数据跑很多遍**（CSV 里 50 个账号，每个账号跑一遍）；
- 每次跑完**留下记录和报告**，能看出哪次开始失败的；
- 下一轮让 Jenkins 用命令行跑同一个测试集。

### 用户看到的样子

**左侧栏**：目录树上方加一个切换「接口 | 测试集」。切到「测试集」时列出这个项目的测试集：

- 新建、重命名、复制、删除（删除要确认；**测试集不进回收站**，回收站的表只认目录 / 接口 / 环境）、拖动排序；
- 每行显示名字、步骤数、最近一次运行的结果小圆点（绿 / 红 / 灰，没跑过不显示）；
- 点一下打开测试集标签页。

**测试集标签页**（`kind: 'suite'`）。顶部：名字（双击改名）、环境下拉（默认当前环境）、「运行」按钮（运行中变「停止」）。下面四个页签：

1. **步骤**
   - 一张可拖动排序的列表，每行：启用开关 · 序号 · 方法 + 接口名（灰字显示所在目录）· 失败时（「继续」/「跳过本轮剩下的」）· 等待（毫秒）· 删除。
   - 「添加接口」：弹出目录树多选（勾目录就是把它下面的接口按树的顺序全加进来，WebSocket 接口不能加）。同一个接口可以加多次。
   - 点开一行：显示这个步骤**额外的**断言和提取变量（复用接口「断言」页签的那个组件），说明「接口自己的断言照样会跑，这里的是在它之后追加的」。
     还有一个「打开接口」链接。
   - 接口被删了：那一行标红「接口已删除」，运行时这一步算出错。
2. **数据**（数据驱动）
   - 「不用数据」/「CSV」/「JSON」。CSV 第一行是列名；JSON 是对象数组。可以粘贴，也可以选文件（读进来存在测试集里，不另存文件）。
   - 下面预览前 20 行（表格），显示「共 N 行，会跑 N 轮」；格式不对时显示哪一行哪里不对。
   - 说明：「每一行跑一轮。列名就是变量名，接口里写 `{{列名}}` 就能用；脚本里用 `pm.iterationData.get('列名')`。数据变量优先于环境变量。」
   - 上限：1000 行、2 MB。
3. **设置**
   - 不用数据时跑几轮（1–100，默认 1）；
   - 每个请求之间等多久（毫秒，默认 0；步骤上单独设的等待在它之外）；
   - 请求超时（默认跟全局设置）；
   - 一行灰字说明：「运行时提取、脚本设置的变量只在这次运行里有效，不会改环境里保存的值；Cookie 每次运行从空开始，步骤之间共用；不记历史。」
4. **运行记录**
   - 列表：时间、来源（客户端 / 命令行）、环境、谁跑的、结果（通过 / 失败 / 停止 / 出错）、通过数 / 总数、用时。最多显示最近 100 次。
   - 点一条打开报告（见下）。可以删除单条记录（editor 以上）。
   - 没登录（只用本机）时这一页显示「登录后运行记录会保存到云端，同事也能看到」，运行照样能跑，只是不留记录。

**运行中**：标签页正文换成进度视图（和现在的批量运行差不多）——进度条「第 2/50 轮 · 第 3/6 步」，一行一个步骤结果，失败的标红，
可以「只看失败」。跑完自动切到这次的报告。

**报告**（运行完成后、或者从运行记录里打开）：

- 顶部汇总：结果、轮数、请求数、通过 / 失败、断言通过 / 失败、总用时、平均响应时间。
- 有数据驱动时：按轮分组，每轮标题显示这一轮的数据（前几个字段），失败的轮默认展开。
- 每一步：状态码、耗时、大小、断言结果；失败的步骤能展开看**实际发出的请求**和**响应**（响应体只存失败步骤的、最多 32 KB）。
- 「导出报告」：下载一个单独的 HTML 文件（样式内联，不引外部资源），可以发给别人或贴到工单里。

**批量运行标签页**加一个按钮「存为测试集」：把当前勾选的接口按顺序建成一个新测试集，然后打开它。

**网页版**（云端 `SERVER_SEND=0`）：「运行」按钮可以点，点了提示「网页版不能运行测试集，请在客户端里运行」，带下载客户端的入口（照 `ConnectionStatus.vue` 的做法）。
编辑测试集、看运行记录和报告在网页版上都能用。

### 数据（已建好：v15）

```
suites(id, project_id, name, description, position, steps, data, settings, created_at, updated_at, rev)   -- 同步
suite_runs(id, suite_id, project_id, source 'app'|'cli', environment_name, status 'passed'|'failed'|'stopped'|'error',
           summary, result, triggered_by, label, started_at, finished_at)                                  -- 只在云端
```

- `steps`（JSON 数组）：`[{ id, apiId, enabled, onFail: 'continue' | 'skipIteration', delayMs, assertions: [], extracts: [] }]`。
  `assertions` / `extracts` 的格式和接口上的一样（`dto.toAssertions` / `dto.toExtracts` 清洗）。
- `data`（JSON 或 null）：`{ format: 'csv' | 'json', fileName, text }`。存原文，运行时再解析。
- `settings`（JSON）：`{ iterations, delayMs, timeoutMs }`，以后加东西都往这里放。
- `suite_runs.summary`：`{ iterations, requests, passed, failed, errors, assertions: { passed, failed }, durationMs, avgMs }`。
- `suite_runs.result`：`{ iterations: [{ index, data, steps: [{ stepId, apiId, name, method, url, status, timeMs, size, ok,
  skipped, error, tests: [{ name, passed, message }], request?, response? }] }] }`。`request` / `response` 只有失败的步骤才带；
  整个 `result` 超过 2 MB 时去掉所有 `request` / `response` 再存，并在 summary 里记 `truncated: true`。
- `label`：留给第九轮命令行用（比如 Jenkins 的构建号），这一轮界面上只显示，不用填。
- 环境存**名字**不存 id：第九轮命令行按名字选环境，记录里看名字也更直观。
- 每个测试集只留最近 100 条运行记录，插入新的时删掉更早的。

### 接口

| 方法 | 路径 | 权限 | 说明 |

  （`ORDER` 里也要加）。看一下 `lib/sync/index.js`、`lib/gateway/sync/*` 是不是按 `ENTITIES` 自动处理的，有写死实体名单的地方都补上。
  项目权限过滤（成员只能拉自己项目的）照 `environment` 那一条。
- `guard` 的 `byParam` 要能认 `suite` 和 `suite-run`（看 `lib/api/guard.js` 怎么认 `api` 的）。

  删掉接口时测试集**不用**跟着改（运行时标「接口已删除」）。

### 运行（`POST /suites/:id/run`）

请求体：`{ environmentId, mockBase }`（`mockBase` 和 `/send` 一样，内置 Mock 环境用）。

- 云端 `!serverSendEnabled()` 时直接 409 `SERVER_SEND_DISABLED`（和 `/send` 同一个函数）。
- 返回 NDJSON（用 `lib/api/ndjson.js`），事件：
  - `{ type: 'start', runId, iterations, steps }`
  - `{ type: 'step', iteration, index, ...步骤结果 }`（每步跑完一条）
  - `{ type: 'done', status, summary, saved: true | false, warning? }`（`saved` 是运行记录有没有存上云端，`warning` 是没存上的原因）
- 浏览器断开（`res` 的 `close`）就停：当前请求取消，后面不再发，状态记 `stopped`，**照样存运行记录**。
- 跑完之后存记录：
  - **在网关上**：登录状态下用 `lib/gateway/cloud.js` 的 `requestJson` 带当前用户的会话调云端 `POST /suites/:id/runs`
    （看 `account.js` 的 `forwardCloudOnly` 是怎么带会话的，照着做）。没登录就不存（`saved: false`，不算错）。
    这个测试集刚在本机新建、还没同步上云时，云端会因为找不到测试集报错 —— 先触发一次同步再重试一次，还不行就
    `saved: false` + `warning: '运行记录没有保存：…'`。
  - **在云端上**（开了 `SERVER_SEND=1`）：直接写库。

### 执行模块（`lib/suite-runner.js`，**第九轮命令行要直接用**）

```js
runSuite({
  handle,            // 数据库
  preparer,          // send.js 的 createPreparer(ctx)
  project, suite,    // 已经查好的行（DTO）
  environmentId,     // 可以是内置 Mock 环境
  mockBase,
  who,               // { user: { id }, role }
  signal,            // AbortSignal
  fileRoots,
  onEvent            // function (event) —— 上面那几种事件
}) → Promise<{ status, summary, result, environmentName, startedAt, finishedAt }>
```

不碰 `req` / `res`、不碰 express、不写库。每一步：

1. 用接口当前保存的内容拼 `body.request`（方法、地址、参数、请求体、鉴权、脚本 —— 看前端 `specFromApi` 和 `dto` 确认字段对得上），
   断言 / 提取 = 接口自己的 + 步骤追加的；调 `preparer.prepare(who, project, { apiId, environmentId, mockBase, request, options: { skipHistory: true, timeoutMs } })`。
2. 把这次运行累积的变量改动叠到 `prepared.scopes` 上：项目层、环境层各有一份内存里的改动（`{ set, unset }`，照 `send-core` 的 `mergeVarChanges`），
   数据驱动这一轮的那一行放进新的 `scopes.data`。
3. `prepared.cookies` 换成这次运行自己的那份 Cookie（运行开始时为空，每步跑完把 Cookie 增量合进来）。
4. `sendCore.run(prepared, { signal, fileRoots })`，拿到结果后把脚本 / 提取对项目、环境变量的改动合进内存里的改动（**不写库**）。
5. 算这一步过没过：请求出错，或者有一条断言 / 测试没通过，就是失败。失败且 `onFail === 'skipIteration'` 时这一轮剩下的步骤标「跳过」。

运行结果的 `status`：全部通过 `passed`；有失败 `failed`；被停 `stopped`；准备阶段就出错（比如环境不存在）`error`。

**数据驱动的变量层**（`lib/send-core.js`、`lib/scripts/*`）：

- 变量优先级变成「项目 → 目录 → 环境 → **数据** → 本次请求的临时变量」：`mergeScopes` 在环境之后、`transient` 之前叠 `scopes.data`；
  脚本里 `pm.variables.get` 的查找顺序同样改。`scopes.data` 没有时一切照旧（**普通发送、批量运行行为不能变**）。
- 脚本里加 `pm.iterationData`：`get(key)`、`has(key)`、`toObject()`，只读。没有数据时 `get` 返回 `undefined`、`toObject()` 返回 `{}`。
- CSV 解析写在 `lib/suite-data.js`（运行和 `preview-data` 共用，前端不再写一份）：第一行列名、逗号分隔、双引号转义（`""`）、
  引号里可以有换行和逗号、去掉 UTF-8 BOM、跳过全空的行、`\r\n` 和 `\n` 都认。值一律是字符串。JSON 要求对象数组，值不是字符串的转成字符串（对象 / 数组 `JSON.stringify`）。

**存进记录的请求要打码**：`prepared.secretValues`（保密值）在请求的地址、请求头、请求体里替换成 `******`；`Authorization`、`Cookie` 头的值替换成 `******`。

## 2. 简单压测（session1）

### 要解决的问题

上线前想知道「这个接口 50 个并发扛不扛得住、P95 多少」，现在只能去找别的工具。不需要复杂的场景编排，一个接口、一组参数就够。

### 用户看到的样子

**入口**：接口标签页的「发送」按钮旁边的下拉里加「压测…」。打开一个压测标签页（`kind: 'load'`，每个接口一个，再点就切过去），
标题「压测 · 接口名」。**开始时拍下接口标签页当前的内容**（没保存的修改也算），之后改接口不影响正在跑的。

**设置**（左边或上面一栏）：

- 环境（默认当前环境）；
- 并发数：1–200，默认 10；
- 停止条件：「按次数」（总请求数 1–100000，默认 1000）或「按时长」（5–600 秒，默认 30）；
- 预热：几秒内把并发从 1 慢慢加到设定值（0–60，默认 0）；
- 超时：每个请求最多等多久（默认 10000 毫秒）；
- 算成功的状态码：默认「2xx 和 3xx」，可以改成填具体的（比如 `200,201`）；
- 一行灰字：「压测只看状态码和响应时间：不跑脚本、不跑断言、不记历史。变量在开始时按环境算一次。」

**开始前确认**：环境名里带「生产」「线上」「prod」（不分大小写）时，弹红色确认框「你要压测的是生产环境：xxx。确定继续吗？」。
所有情况下开始按钮旁都有一句「压测会对目标服务器产生真实压力，请先和接口负责人确认」。

**运行中**：

- 顶部数字实时跳：已发 / 成功 / 失败、当前 QPS、平均响应时间、P95、正在进行的请求数、已用时间；进度条（按次数时按次数、按时长时按时间）。
- 一张图：横轴时间（秒），两条线 —— 每秒请求数、每秒平均响应时间（右侧第二条纵轴）；失败多的那一秒在下面标红条。
  用 SVG 自己画，**不加图表库**。
- 「停止」按钮。

**结束后**：汇总表 —— 总请求数、成功、失败、错误率、总用时、平均 QPS、最小 / 平均 / 最大、P50 / P90 / P95 / P99；
状态码分布（`200 × 980`、`500 × 20`）；错误分组（`超时 × 12`、`连接被重置 × 3`，每组带一个示例信息）。
「复制结果」把汇总复制成一段文字（方便贴到群里）。同一个标签页里可以再跑一次，上一次的汇总留在下面「上次结果」里对比。

**不存库**：压测结果只在这个标签页里。设置（并发数、次数等）按接口记在 `localStorage` 里，下次打开压测标签页沿用（读写包 try/catch）。

**网页版**：下拉里的「压测…」灰掉，悬停提示「网页版不能压测，请在客户端里使用」。

### 接口

`POST /projects/:pid/load`（viewer），请求体和 `/send` 一样（`request`、`apiId`、`environmentId`、`mockBase`），多一个
`load: { concurrency, mode: 'count' | 'duration', count, durationSec, rampUpSec, timeoutMs, okStatus: [] }`（`okStatus` 空表示 2xx/3xx）。

- **只在本机网关上挂这个路由**（`ctx.localSend` 为真时），云端不管 `SERVER_SEND` 开没开都不挂 —— 从团队共用的服务器上压测别人的接口风险太大。
  云端收到请求就是 404，前端靠 `useGatewayStore().cloudSendBlocked` / 是不是在客户端里来决定按钮灰不灰。
- 参数越界一律 400（不是悄悄截断），提示写清范围。
- 返回 NDJSON：
  - `{ type: 'start' }`
  - `{ type: 'tick', t, sent, ok, failed, active, qps, avgMs, p95Ms, failedInSecond }`，**每秒一条**（不是每个请求一条）；
  - `{ type: 'done', status: 'finished' | 'stopped', summary }`，`summary` 字段见上面「结束后」。
- 浏览器断开就停：不再发新的，在途的全部取消。
- 一个网关同时只能跑一个压测，第二个返回 409「已经有一个压测在跑」。

### 执行模块（`lib/load-runner.js`）

- 用 `createPreparer(ctx).prepare(who, project, body, …)` 拿准备好的请求，`options.scripts` 设成 false（不跑脚本），断言、提取清空。
- 然后**同一份 prepared 反复执行**。要点：
  - **复用连接**：每次运行建一对 `http.Agent` / `https.Agent`（`keepAlive: true`，`maxSockets` = 并发数），跑完 `destroy()`。
    现在 `lib/executor.js` 里写死了 `agent: false`，给它加一个可选的 `options.agent`（不传时行为完全不变 —— **普通发送不能受影响**），
    走代理时怎么办你看着处理（代理那条路不复用也可以），交接里写清楚。
  - **响应体不要攒在内存里**：压测不需要响应体，读完就丢；看 executor 有没有现成的办法，没有就加一个可选项（同样不传时行为不变）。
  - 也可以评估「变量算一次，之后直接用 Node 的 `http.request` 发」是否更简单可靠 —— 二选一，交接里说为什么。
- 并发控制：`concurrency` 个「工人」各自循环发请求，预热期间按时间线性放出工人。
- 统计：响应时间用**固定桶的直方图**（比如 1 ms 一个桶到 10 秒、之后 100 ms 一个桶到 300 秒），不要把每个请求的耗时都存下来
  （按时长跑 10 分钟可能有几百万个）；每秒一个小结（请求数、失败数、耗时总和）给图用。
- 错误分组：按状态码分组；网络错误按 `error.code`（超时、连接被拒、连接被重置、DNS 解析失败……）翻成中文分组。
- 超时用 `timeoutMs`，到了就算失败「超时」。
- 跑完关掉所有连接；被停时取消在途请求。

### 前端

- 运行逻辑放 store（切标签页不能断），照 `stores/runner.js`。
- 图表组件写成 `web/src/components/load/` 下一个独立的 `.vue`，输入是每秒小结的数组。

**没有新接口以外的接口**：这一节只有一条新路由 `POST /projects/:pid/load`（NDJSON）。
`lib/executor.js` 的两个新选项都是可选的，**不传时行为和以前一模一样**（自测里有专门两条盯着
「不传 agent / discardBody 时响应体照常拿到、truncated 还是 false」）。

**executor 是怎么改的（审阅重点）：**

```js
var agent = opts.agent || false;          // 直连那条路：agent: agent（以前写死 false）
if (opts.discardBody) return;             // readResponse 的 data 回调里：只数大小，不攒内容
```

- **`agent` 只在直连时生效**（`directOptions.agent`）。走代理的两条路（http 绝对地址、https CONNECT
  隧道）**仍然写死 `agent: false`**：那两条路要按跳改写请求头、隧道还要自己 `createConnection`，
  复用连接的收益和风险都不划算。交接里明说这件事，见下面「走代理时怎么处理的」。
- **`discardBody` 不设 `truncated`**：它和「响应太大被截断」不是一回事（一个是主动不要，一个是被动丢了），
  混在一起会让以后读这块代码的人以为数据不完整。

**为什么直接把 `executor.execute` 反复调，而不是 `sendCore.run`（计划里说的「二选一」）：**

1. **`sendCore.run` 不接受 `agent` / `discardBody`** —— 这两个恰好是压测最需要的（复用连接、不攒响应体），
   它自己拼 `execOptions` 且这个选项表不对外开放；
2. 它每个请求都会重建变量表、跑脚本 / 断言链、建 Cookie jar —— 压测一样都不需要，
   而**它是 session2 这一轮在改的文件**，我不该为了压测去动它；
3. prepare 出来的东西照用（变量分层、保密值、公共请求头、鉴权继承都由 `createPreparer(ctx).prepare()`
   算好），所以「和发送同一套规则」这条没有破。

于是：**开始前** `variables.resolveSpec(prepared.spec, mergeScopes(prepared.scopes))` 算一次，
拿到最终地址、`missingVariables`（放进 `start` 事件，界面上会提示「这些变量没有值」）、
以及「要不要走代理、建 http 还是 https 的 Agent」；之后每个请求发同一份。

**走代理时怎么处理的：**

- 代理设置照 `prepared.proxy` + `proxySettings.forTarget(setting, url)` 算（和发送一致）；
- **走代理时不建 Agent**（见上），也就是不复用连接。压测走代理本身就是拿代理当瓶颈，
  复用连接的收益很小，而「按跳改写请求头 + CONNECT 隧道自己造 socket」的复用要改执行器的核心路径，
  风险远大于收益；
- 自测脚本里顺手发现：**沙箱带 `http_proxy` 环境变量**时，`127.0.0.1:9` 那种「连不上」会被代理
  变成一个 **502 响应**（于是错误分组里看不到「连接被拒绝」）。这不是产品 bug —— 真机上代理该不该
  拦本地地址由用户自己的 noProxy 决定；但探针里必须先 `delete process.env.http_proxy` 才验得到直连那条路。
  这条已经写进探针开头的注释。

**几个实现上的决定：**

1. **参数越界一律 400**（不悄悄截断）：用户填 5000 个并发却只跑了 200，量出来的数是错的，比报错更坑。
   前后端各有一份范围表（`lib/load-runner.js` 的 `LIMITS` 和 `web/src/utils/load.js` 的 `LOAD_LIMITS`），
   服务端那份是**把关的**，前端那份只用来限制输入框。
2. **按次数跑时「先占名额再发」**：判断和自增之间没有 `await`，所以总量正好是 `count`，
   不会被并发多打出去几十个（自测里断言了靶子服务正好收到 50 个）。
3. **被停时在途的算「已取消」**，既不算成功也不算失败（`summary.aborted`），
   界面上单独说一句 —— 不然「停止」会凭空多出几十个失败，把错误率算歪。
4. **直方图是固定桶**（1ms 一桶到 10 秒，之后 100ms 一桶到 300 秒）：按时长跑十分钟可能有几十万个请求，
   存数组会吃光内存。P95 报的是**桶的下界**（「不超过这个值」）。
5. **tick 是累积的、秒小结是每秒的**：`avgMs` / `p95Ms` 是累计（顶部的数字要的是「到目前为止」），
   `secondAvgMs` / `qps` / `failedInSecond` 是这一秒的（图上要的是「每秒」）。两者都发，前端各取所需。
6. **HTTP 状态码不进「错误分组」**：那是给网络层错误的（超时、连接被拒绝……），
   状态码有单独的「状态码分布」。两处都记会让人对不上数。界面上错误分组为空时写了一句说明。
7. **压测不带 Cookie**（`options.cookies: false`）：并发几百个请求共用一个 cookie jar 只会互相覆盖，
   量出来的数没有意义（要带就自己在请求头里写）。
8. **请求快照在「开始」那一刻拍**：优先取那个接口标签页里编辑中的 spec（没保存的修改也算），
   接口标签页没开着就现拉一份详情 —— 之后改接口不影响正在跑的这一次。
9. **生产环境确认在前端做**（环境名里带「生产 / 线上 / prod」不分大小写就弹红色确认框），
   服务端不管这件事：它只是执行器，确认是界面上的事。
10. **图表不加库**：坐标计算放在 `utils/load.js` 的 `chartGeometry`（纯函数、能单独跑断言），
    组件只往里填 `<path>` / `<rect>`。
