## T5 gRPC 补全 · 后端一：服务端反射、断言和提取变量（session1，T3 通过后）

### 背景
用户要「gRPC 补全」。T1 已经做好 `lib/grpc.js`（解析 proto、一元 / 服务端流调用）和 `lib/api/grpc.js`（`/grpc/parse`、`/grpc/call`），接口约定看 `ateam show T1`。
这一轮补三样：服务端反射（不用导 proto）、断言和提取变量（本任务）；客户端流和双向流（T6，本任务通过后才派）；界面（T7）。

### 接口约定

### 数据：`api.extra.grpc` 加两个字段（`dto.toApiGrpc` 要认）
```json
{ "source": "proto",
  "reflection": { "descriptorSet": "<base64 的 FileDescriptorSet>", "fetchedAt": 1759650000000 } }
```
- `source`：`proto`（用导入的 proto 文件，默认）或 `reflection`（用反射拿到的描述）。
- `reflection` 没反射过是 null；`descriptorSet` 超过 2 MB 就不存（`toApiGrpc` 丢掉，并且 `/grpc/reflect` 的响应里给 `tooLarge: true`）。
- 断言、提取变量**不另存**，就用接口上已有的 `extra.assertions` / `extra.extracts`（`dto.apiAssertionsOf` / `apiExtractsOf`，HTTP 接口用的同一份）。

### `POST /projects/:pid/grpc/reflect`（权限同 `/grpc/call`；只在本机网关）
请求：`{ "apiId", "environmentId", "url", "tls", "metadata" }`（地址、metadata 的 `{{变量}}` 照 `/grpc/call` 一样替换）。
成功：`{ "services": [和 /grpc/parse 一样的形状], "descriptorSet": "base64", "fetchedAt": 1759650000000, "tooLarge": false }`。
- 先试 `grpc.reflection.v1.ServerReflection`，服务端返回 UNIMPLEMENTED 再试 `grpc.reflection.v1alpha.ServerReflection`。
- 流程：`list_services` → 对每个服务 `file_containing_symbol` → 把返回的 `file_descriptor_proto` 收齐，**缺的依赖按 `file_by_filename` 继续要**，直到齐了；`grpc.reflection.*` 服务本身不列出来。
- 反射用的 proto（`reflection.proto` v1 / v1alpha）以字符串常量放在 `lib/grpc-reflection.js` 里，不依赖外部文件。
- 失败返回 400，中文：两版都 UNIMPLEMENTED →「服务端没开反射，请导入 proto 文件」；连不上、超时照 `STATUS_HINTS`。反射整体 10 秒超时。

### `/grpc/parse`、`/grpc/call` 也认 `descriptorSet`
- 请求体里有 `descriptorSet`（base64）时用它，**不再要求** `protoFiles`；两个都有时以 `descriptorSet` 为准。
- `descriptorSet` → 服务清单：用 protobufjs 的 `ext/descriptor`（`Root.fromDescriptor`）；→ 调用：用 proto-loader 的 `loadFileDescriptorSetFromBuffer`（选项和现在的 `loaderOptions` 一样）。示例生成、服务清单共用现在的代码。
- base64 解不开或不是合法的 FileDescriptorSet：400「反射数据损坏，请重新获取」。

### `/grpc/call` 加断言和提取变量
请求体多两个可选字段 `assertions`、`extracts`，形状和 HTTP 接口的一样（`lib/assertions.js` 的 `toAssertions` / `toExtracts` 认的那种）。
调用结束时按下面这个「响应」跑断言和提取，**结果放进 `end` 那一行**：
- 状态码 → gRPC 状态码的数字（OK 是 0）；
- 响应头 → metadata 和 trailers 合在一起（同名取第一个值）；
- 响应体 → 一元调用是那条消息的 JSON；服务端流是全部消息组成的 JSON 数组；
- 响应时间 → `durationMs`。

`end` 行多出：`"tests": [{ "name", "passed", "message" }]`（和 HTTP 发送结果里测试结果的形状一样），`"extracted": [{ "key", "value", "scope" }]`。
提取到的变量**照 `/send` 的做法写回环境 / 项目变量**（看 `lib/send-core.js` 的 `applyExtracted` 是怎么写库的，复用它，别另写一份）。准备阶段出错（`error` 行）时不跑。

### 要做的事
1. `lib/grpc-reflection.js`（新）：反射客户端 + 两版 reflection.proto 常量。
2. `lib/grpc.js`：支持 `descriptorSet`；把「按 protoFiles 或 descriptorSet 拿到服务构造函数和方法」整理成一个导出的函数（T6 的流式会话要用）；`end` 前跑断言和提取。
3. `lib/api/grpc.js`：`/grpc/reflect`；`/grpc/parse`、`/grpc/call` 认 `descriptorSet`、`assertions`、`extracts`。
4. `lib/api/dto.js`：`toApiGrpc` 认 `source`、`reflection`。
5. 自测：临时目录里起一个**开了反射**的真实 gRPC 服务（`@grpc/reflection` 没装，不能装；可以用 grpc-js 自己实现一个最小的反射服务：只回 list_services 和 file_containing_symbol / file_by_filename，描述用 protobufjs 生成），再起一个**没开反射**的；分别调 `/grpc/reflect`，把服务清单打出来；用拿到的 `descriptorSet` 调 `/grpc/call`；带两个 import（含 google/protobuf/timestamp）的 proto 也要能通过反射收齐依赖。断言：状态码等于 0、JSON 字段等于某值、响应时间小于某值、metadata 某个头存在，一条故意失败的；提取一个字段到环境变量，调完读环境确认写进去了。

### 不要做的事
- 不要改 `package.json`（不加 `@grpc/reflection`）。
- 不做 T6 的客户端流 / 双向流；不改前端。

### 验收标准
（与 --accept 一致）

## T6 gRPC 补全 · 后端二：客户端流和双向流（session2，T5 通过后）

### 背景
T1 只做了一元调用和服务端流，客户端流 / 双向流在 `/grpc/call` 里直接报「这一版只支持一元调用和服务端流」。这两种调用要能**边连着边发**，所以和 Socket.IO 一样做成**会话**。
T5 已经把「按 protoFiles 或 descriptorSet 拿到服务构造函数和方法」整理成 `lib/grpc.js` 里导出的函数，直接用它。接口约定看 `ateam show T1`、`ateam show T5`。

### 接口约定
**路由形状照 `/sio` 来**（`lib/api/sio.js`：建会话、`GET /sio/:id/events` 收 NDJSON 事件、`POST /sio/:id/send`、`DELETE /sio/:id`），会话管理照 `lib/sio-sessions.js`（只有创建者能访问，别人一律同一个 404；空闲回收；同一个人的会话数上限）。具体：
- `POST /projects/:pid/grpc/streams`：请求体和 `/grpc/call` 一样（不带 `message`），只接受客户端流 / 双向流的方法（一元和服务端流返回 400「这个方法请直接调用」）。成功 `{ "id": "gs_xxx" }`。
- `GET /grpc/streams/:id/events`：NDJSON，事件：
  - `{"type":"start","target","tls","missing","note"}`
  - `{"type":"metadata","metadata":{...}}`
  - `{"type":"sent","data":{...},"at":...}`（发出去的每一条，变量替换后的）
  - `{"type":"message","data":{...},"at":...}`（收到的每一条）
  - `{"type":"end","status":{...},"trailers":{...},"durationMs":...}`（和 `/grpc/call` 一样带 T5 的 `tests` / `extracted`，响应体按「收到的全部消息组成的数组」，客户端流就是那一条）
  - `{"type":"error","error":"中文"}`
  事件要先缓存，页面晚连上 / 断开重连时从头补发（照 sio 的做法）。
- `POST /grpc/streams/:id/send`：`{ "message": "JSON 文本，可带 {{变量}}" }`，变量按建会话时的环境替换；不是 JSON 对象 400；会话已经结束 409「会话已经结束」。
- `POST /grpc/streams/:id/end`：结束发送（half-close，`call.end()`），之后服务端还可以继续回消息直到 `end`。
- `DELETE /grpc/streams/:id`：取消（`call.cancel()`）并删掉会话。
- 同时把 `/grpc/call` 里那句提示改成「客户端流、双向流请用流式会话（POST /grpc/streams）」，界面会走新接口。
- 只在本机网关上有（和 `/grpc/call` 同一个开关）。

### 要做的事
1. `lib/grpc-sessions.js`（新）：会话注册表、调用、事件缓存、回收。
2. `lib/api/grpc.js`：上面几条路由。
3. `lib/grpc.js`：如有需要做小改动（比如把会话也要用的部分导出）。
4. 自测：临时目录里起真实 gRPC 服务，一个客户端流方法（收齐后回总数）、一个双向流方法（每收一条回一条，收到 `end` 后再回一条再结束）；建会话、连事件流、发 3 条、`end`，把事件逐行打出来；再测：别人的会话 id 访问 404、`DELETE` 后服务端收到 cancel、会话结束后再发 409、事件流断开重连能补到前面的事件、空闲回收生效（可以把回收时间调小测）。

### 不要做的事
- 不改前端；不改 `package.json`；不改 `lib/admin.js`（路由都挂在 `lib/api/grpc.js` 这个已经挂好的 router 上）。

### 验收标准
（与 --accept 一致）

## T7 gRPC 补全 · 前端（session1，T5、T6 通过后）

### 背景
T5（反射、断言和提取）、T6（客户端流 / 双向流会话）的后端都好了，约定看 `ateam show T5`、`ateam show T6`。T3 做好的 gRPC 标签页（`web/src/components/grpc/`）上把它们接进去。

### 用户看到的样子
- **Proto 来源**：「Proto 文件」页签改名「服务定义」，顶上一个切换「导入 proto 文件 / 服务端反射」（存在 `extra.grpc.source`）。
  - 选「服务端反射」：一个「从服务获取」按钮（用当前地址、TLS、metadata 调 `/grpc/reflect`），获取后显示服务数、方法数和获取时间，结果存进 `extra.grpc.reflection`（随接口保存、同步）；之后打开接口直接用存下的 `descriptorSet` 调 `/grpc/parse` 填服务 / 方法下拉，不用每次连服务端。失败显示后端给的中文；`tooLarge` 时提示「描述太大没有保存，每次打开需要重新获取」。
  - 调用、建会话时按来源带 `protoFiles` 或 `descriptorSet`。
- **断言、提取变量**：加一个「断言」页签，**复用 HTTP 接口那套可视化断言 / 提取表格组件**（找到它用的组件直接用，不要另写），字段说明改成 gRPC 的含义：状态码 = gRPC 状态码（0 是 OK）、响应头 = metadata 和 trailers、响应体 = 消息 JSON（服务端流 / 双向流是数组）。存进接口的 `extra.assertions` / `extra.extracts`，调用时带上。
  响应区加「测试结果」页签，显示 `end.tests`（和 HTTP 的测试结果一样的样子）；`extracted` 有值时提示「已提取 N 个变量」。
- **客户端流 / 双向流**：方法下拉里这两种不再禁用。选了之后：
  - 「调用」按钮变成「连接」，连上后变「断开」；
  - 消息编辑器下面「发送」（发当前消息框里的内容）和「结束发送」按钮，常用消息照样能选；
  - 响应区「消息」页签变成一个双向的消息列表（发出 / 收到 用颜色或箭头区分，带时间、可展开 JSON），连接、metadata、结束状态也作为一行显示 —— 和 Socket.IO 标签页的消息列表一样的体验（能复用它的列表组件就复用）；
  - 结束后状态、Trailers、测试结果照常显示。
- grpcurl 命令：反射来源时不带 `-proto`；客户端流 / 双向流时 `-d @` 并提示从标准输入逐条输入。
- 网页版：「从服务获取」「连接」和「调用」一样灰掉并提示在客户端里使用；已保存的反射结果在网页版里不能解析（没有 `/grpc/parse`），下拉照 T3 的做法只显示已保存的服务 / 方法。

### 不要做的事
- 不改后端；不改帮助文档（主会话写）。

（与 --accept 一致）
