## 2. 导出 OpenAPI（session1，第 1 节之后）

### 要解决的问题

现在能导入 OpenAPI，不能导出。别的平台、网关、代码生成工具都认 OpenAPI。

### 用户看到的样子

- 现在「导出为 JSON」的地方（项目、目录的导出入口，找一下在哪），旁边加「导出为 OpenAPI」。
- 点了弹一个小框：格式 JSON / YAML（默认 YAML），「导出」→ 下载文件 `<项目或目录名>.openapi.yaml`。
- 提示一行：「变量（{{host}} 这类）原样保留；鉴权只导出类型，不导出值。」

### 接口

`GET /projects/:pid/export/openapi?folderId=&format=json|yaml`（viewer）。下载方式照抄现在的 `export/json`
（`lib/api/postman.js`）。转换逻辑单独放 `lib/openapi-export.js`，纯函数，输入是项目 / 目录 / 接口 / 示例的 DTO。
YAML 用已经在依赖里的 `js-yaml`。

### 转换规则（OpenAPI 3.0.3）

- `info.title` = 项目名（导出目录时是「项目名 - 目录名」），`info.version` = `'1.0.0'`，`info.description` = 项目说明。
- **路径**：接口地址去掉开头的「`{{变量}}`」或「`http(s)://主机[:端口]`」，去掉 `?` 后面的部分。
  路径里的 `:id` 和 `{{id}}` 都转成 `{id}`，并作为 path 参数。去完是空的就是 `/`。
- **servers**：地址里出现过的字面主机（`https://api.example.com`）去重后放进 servers；开头是 `{{host}}` 这类变量的，
  servers 里放 `{ url: '{{host}}', description: '变量，导入方自己替换' }`（同名变量只放一次）。
- 同一个「方法 + 路径」有多个接口时：第一个正常导出，后面的跳过，并在返回的文件开头注释里列出跳过了哪些
  （YAML 用 `#` 注释；JSON 放进 `info['x-apiloop-skipped']`）。
- **tags**：接口所在的顶层目录名；根目录的接口不打 tag。tags 列表按目录树顺序。
- **operation**：`summary` = 接口名，`description` = 说明，`operationId` 不生成。
- **parameters**：query、path、header（跳过 `Content-Type`、`Authorization`、`Cookie`，以及停用的行）。
  `example` 用表里的值（变量原样），`description` 用说明列，类型一律 `string`。
- **requestBody**：
  - raw 且是 JSON：`application/json`，`example` 是原文解析后的值（解析失败就当字符串），`schema` 按示例推断
    （对象 → properties，数组 → items 取第一个元素，数字 integer / number，布尔，null → nullable string）；
  - urlencoded / formdata：对应的 content type，`schema.properties` 每个字段 string，文件字段 `format: binary`；
  - 其他 raw（text / xml）：对应 content type，`schema: { type: string }`，example 是原文；
  - none / binary：不写（binary 写 `application/octet-stream` + `format: binary`）。
- **responses**：每个示例一个，key 是状态码（同状态码多个示例时用 `examples` 多个命名示例）；
  JSON 类型的 `example` + 推断的 `schema`；没有示例就写 `'200': { description: 'OK' }`。
- **鉴权**：项目 / 目录 / 接口上用到的类型生成 `components.securitySchemes`（bearer、basic、apikey 的 header / query），
  operation 上写 `security`。继承的按发送时的规则往上找（`lib/api/shares.js` 的 `authTypeOf` 有现成的逻辑，提出来共用）。
  **不导出任何值**。
- 保密变量、环境变量的值一律不出现（导出里本来也只有 `{{变量}}` 写法）。

### 验收清单

1. 导出整个项目为 YAML，用 Swagger Editor（editor.swagger.io）打开不报错，接口、参数、示例都在。
2. 把导出的文件再用 apiloop 的 OpenAPI 导入导进一个新项目，接口数量、地址、参数对得上。
3. 导出一个目录，只包含这个目录下的接口。

## 3. 从 OpenAPI 同步更新（session2）

### 要解决的问题

后端用 Swagger 维护接口，接口一改，现在只能整个重新导入 —— 会重复出一套，或者把自己写的脚本、示例、Mock 覆盖掉。
要能「只更新变了的部分」。

### 用户看到的样子

- 入口：
  - 目录树空白处右键「从 OpenAPI 同步更新」；
  - 目录右键（这个目录是从 OpenAPI 导入的、或者里面有从 OpenAPI 导入的接口时）同样的菜单项；
  - OpenAPI 导入成功后的提示里加一句「以后后端改了接口，可以在目录树右键『从 OpenAPI 同步更新』」。
- 弹窗：
  1. 地址输入框（记住上次用的地址，自动填上）；也可以切到「粘贴内容」。「检查更新」按钮。
  2. 检查完列出三组，每组可以全选 / 单选：
     - **新增**（文档里有、项目里没有），默认勾选，显示方法、路径、名称、会放到哪个目录；
     - **有改动**（两边都有但不一样），默认勾选，每行显示改了什么（「地址」「参数：新增 page、删除 size」「请求体字段」「名称」「说明」），
       可以展开看前后对比；
     - **文档里已删除**（项目里有、文档里没了），**默认不勾**，勾了的放进回收站（不是真删）。
  3. 一行灰字：「只更新地址、参数、请求体字段、名称和说明；你写的脚本、示例、Mock、鉴权设置都会保留。」
  4. 「同步所选」→ 完成后提示「新增 x 个、更新 y 个、移到回收站 z 个」，目录树刷新。
- 没有任何变化：显示「已经是最新的」。

### 怎么认出「同一个接口」

- 导入时给每个接口记 `apis.extra.openapi = { key: 'GET /pets/{petId}', operationId?: '...' }`
  （key = 大写方法 + 空格 + OpenAPI 原始路径模板）。
- 匹配顺序：有 `operationId` 且两边一致 → 是同一个；否则比 key；都没有记录的（这个功能上线之前导入的老接口）
  → 用「方法 + 规范化后的路径」比：接口地址去掉开头的 `{{变量}}` / 主机、去掉查询串，`:id`、`{{id}}`、`{id}` 都当成同一种占位符。
- 匹配范围：同步时指定的目录（含子目录）；从空白处进来就是整个项目。
- 记住的来源：`projects.extra.openapiSources = [{ folderId: null | '<目录id>', url, lastSyncedAt }]`，
  按 folderId 区分（导入到哪个目录就记在哪个目录上）。粘贴内容导入的 url 记空串。

### 更新哪些字段

- **名称、说明**：文档里的 summary / description 变了就更新（文档里为空时不清空用户写的）。
- **方法**：一般不会变（方法变了 key 就不同，会被当成删一个、加一个）。
- **地址**：只替换路径部分，用户写的开头（`{{host}}`、`{{baseUrl}}/api` 这类）保留。
- **query / path 参数、请求头**：按名字合并 —— 文档里新加的加上（值用文档的示例值或空），文档里没了的删掉，
  两边都有的**保留用户的值**、更新说明。用户自己加的、文档里从来没有过的请求头（比如 `X-User-Info`）不删：
  只删「上次同步时文档里有、这次没了」的。为此导入 / 同步时在 `extra.openapi.fields` 里记下当时文档给的参数名和请求头名。
- **请求体**：只处理 raw JSON 的顶层字段，规则同上（新加的加上、文档里删了的删掉、两边都有的保留用户的值）。
  用户的请求体不是合法 JSON（比如里面有不加引号的 `{{变量}}`）时不动，改动列表里写「请求体无法自动合并，请手动检查」。
- **不动**：脚本、示例、Mock 设置、鉴权、状态和负责人（第 1 节）、`extra` 里别的字段。
- 新增的接口：和导入一样建（按 tag 放进目录，没有对应目录就建），并记好 `extra.openapi`。
- 移到回收站：用上一轮的回收站（`lib/trash.js` 的 `captureApi` + 删除，和 `DELETE /apis/:id` 同一个事务写法）。

### 接口

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `POST /projects/:pid/openapi/diff` | editor | `{ url? , text?, folderId? }` → `{ added: [...], changed: [...], removed: [...], source }`。拉地址的方式复用现在 `/import/openapi` 的 `fetchSpecText`（客户端里由本机拉，内网地址也行） |
| `POST /projects/:pid/openapi/apply` | editor | `{ url?, text?, folderId?, add: [key...], update: [apiId...], remove: [apiId...] }`。服务端**重新拉一次、重新算一次**再执行（不信任前端传来的内容），一个事务里做完，更新 `openapiSources`。返回 `{ added, updated, removed }` |

- 解析 OpenAPI 复用 `lib/importers.js`。现在它产出的是旧格式的 route，没有带「原始路径模板」和 operationId ——
  给 route 加上 `openapiKey`、`operationId` 两个字段（不影响旧用法），导入落库时写进 `extra.openapi`。
  看清楚 `/projects/:pid/import/routes` → `routes-store.insertRoutes` 这条路怎么把 route 变成接口的，字段从那里带进去。
- 差异计算写成纯函数（`lib/openapi-sync.js`），输入是解析后的 route 列表 + 现有接口 DTO，输出上面的三组。

### 验收清单

1. 从 Swagger 地址导入一个项目 → 在某个接口里写脚本、存示例。
2. 后端改了接口（加了一个 query 参数、删了一个接口、新增一个接口）→ 「从 OpenAPI 同步更新」→ 三组都列出来；
   同步后，新参数出现了、脚本和示例都还在；删掉的那个只有勾了才进回收站。
3. 再点一次「检查更新」→「已经是最新的」。
4. 这个功能上线之前导入的老项目也能同步（按方法 + 路径认出来，不会整批当成新增）。
5. 自己加的请求头（文档里没有的）同步后还在。

**几条实现上的决定（主会话审阅时重点看这几处）：**

1. **状态 / 负责人放进 `tab.spec`**，而不是另开一份界面状态：这样「改了就算有改动」
   （dirty）和「只提交改动过的字段」（`changedFields`）两套现成机制直接复用，
   不用在标签页里再记一份、也不会漏掉 dirty。
2. **写 `extra` 一律「先读出来再合并」**：导入时兜底的那些字段、以及第 3 节要用的
   `extra.openapi` 都不能被冲掉（自测里专门验了 `foo` 和 `openapi.key` 还在）。
3. **不认识的旧状态原样存、原样读回来**，界面按「未设置」显示；只有用户主动改过才会被换掉。
   服务端**不校验**状态取值（以后加了新状态，旧客户端回存时不能把它弄丢）。
4. **负责人只校验「这个人存在」**，不要求是项目成员 —— 管理员不在成员表里，
   但它同样可以被指定为负责人。下拉里的候选来自成员列表（所以未登录时不显示这一项）。
5. **成员列表走一份小缓存**（`utils/projectMembers.js`）：负责人下拉在每个接口标签页上，
   不缓存的话每开一个标签页就拉一次；成员面板拿到新列表后 `setMembers` 塞回去，
   所以刚加的人立刻能选到。
6. **筛选沿用 `filterTree`**：加一个可选的第三参数，目录只有在「下面还有命中的接口」时才保留；
   **按状态筛时目录名自己命中不算**（目录没有状态，留着它反而让人以为里面还有东西），

**几个实现上的决定（审阅时重点看这几处）：**

1. **「新增」拿整个项目比，「有改动 / 已删除」按范围过滤。** 计划写的是「匹配范围：
   同步时指定的目录」，但「新增」的定义是「文档里有、**项目里**没有」—— 只在指定目录里
   比的话，同一个接口在别的目录已经存在，会又建一份出来（默认还是勾上的）。所以匹配
   用全项目的接口，处理再按范围收。这条是自测跑出来的（第一版按范围比，自测直接暴露）。
2. **一个 route 可以配上多条接口**，而且兜底那一级（方法 + 规范化路径）要能配上
   **已经被前两级配过的 route**。同一个文档接口在项目里导了两份时，一份靠 `openapiKey`
   配上、另一份只能靠路径；那个 route 已经被用掉了，跳过它就等于把第二份列进
   「文档里已删除」。这也是自测跑出来的。
3. **「文档里已删除」只列「看起来是从文档来的」接口**：有 `extra.openapi` 记号的，
   或者地址是裸路径的（老导入的 url 就是文档路径 `/pets/:petId`；手写的接口不写
   `{{host}}` / 协议主机根本发不出去，所以裸路径就是「文档来的」）。
   **手写的接口不会被列进去**，也就不会被误删。
4. **参数合并只删「上次同步时文档给过、这次没了」的**（靠 `extra.openapi.fields` 快照）。
   用户自己加的请求头（文档里从来没有过）永远不删；两边都有的**保留用户的值**，
   只更新说明 / 类型 / 必填。
5. **地址只换路径**：文档路径的第一段在现有地址里出现的位置就是「路径的起点」，
   前面那段（`{{host}}`、`{{baseUrl}}/api`）留着。查询串也留着 —— 那是用户写的。
6. **请求体两种形态都管**：OpenAPI 导进来的默认是 `urlencoded` 表单行（`rowsToBody`
   产出的），按名字合并；用户改成 `raw` JSON 的，合并顶层字段。
   **请求体里出现 16 位以上的数字时拒绝自动合并**（`JSON.parse` + `JSON.stringify`
   往返会把 19 位雪花 ID 改成 `...67000`），改成提示「请手动检查」。
   计划里只写了「只处理 raw JSON」，多出来的这一半是因为导入产出的其实是 urlencoded。
7. **apply 重新拉一次、重新算一次**，只按前端勾的 key / apiId 从重算结果里挑 ——
   用户在弹窗里挑的这几分钟里文档可能又变了，而且「算差异」和「改数据」用两份输入
   很容易出现「列表说改 A、实际改了 B」。
