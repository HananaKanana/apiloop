# apiloop 桌面版：本地发请求 + 云端同步（设计稿）

> 状态：**用户已确认（2026-10-01）**。第 10 节的问题都有了结论。
> 优先级：**最高**。在它之前，2.0.0 不按现有形态发布；P10（mock 转发和录制）等其它功能都排在它后面。

## 1. 为什么要做

apiloop 现在的请求是**云端服务器**发出去的。部署在云端之后，有两个根本性问题：

1. 云端访问不到用户本机和内网的地址（`localhost`、`192.168.x.x`、自签名证书的内网 HTTPS），而调试这些接口恰恰是最常见的场景；
2. 用户的电脑一旦切到内网、连不上云端，整个工具就不能用了。

网页本身也替代不了服务器来发请求：跨域、禁止设置的请求头、自签名证书、HTTPS 页面调用 HTTP 地址、公网页面访问内网地址等限制，浏览器都会拦下来。Postman 的做法是桌面程序（或者网页版配合本地 Agent）。我们也这样做。

## 2. 用户已经确认的决定（2026-10-01）

| 问题 | 结论 |
|---|---|
| 形态 | **本地程序 + 云端联网备份**。本地程序负责发请求、显示界面、存数据；云端负责备份、同步和团队协作 |
| 云端还发不发请求 | **不发**。云端只做备份和同步 |
| 分发方式 | **安装包**。先做 Mac 和 Windows |
| 签名 | 先不签名（Mac 第一次打开需要到「系统设置」里点「仍要打开」） |
| 更新 | 先手动下载安装包，以后再加自动更新 |
| 用户和权限 | 在云端。在桌面版里登录云端账号，登录信息保存在本地；数据拉到本地，有网的时候同步 |
| Mock | 放在云端（mock 地址本来就是云端的地址） |

## 3. 整体架构

```
桌面版（Electron 安装包，每人一份）
 ├─ 界面            现有的 Vue 前端，打包在程序里，从本地加载，不需要网络
 ├─ 本地服务        现有的 Express 服务，只监听 127.0.0.1，以「桌面模式」运行
 │   ├─ 发请求       现有执行器原样复用：脚本、Cookie、代理、鉴权、流式、WebSocket
 │   ├─ 本地数据库    现有的 SQLite（node:sqlite），存在用户目录下
 │   └─ 同步引擎      新增：拉取云端变更、推送本地改动、处理冲突
 └─ 登录信息         云端签发的设备令牌，用系统钥匙串加密保存
          ⇅  HTTPS（有网的时候）
云端（现有服务端，以「云端模式」运行）
 ├─ 账号、成员、权限
 ├─ 同步接口         新增：按项目提供「变更流」和「批量提交」
 ├─ Mock            照旧：按云端存的数据提供 mock 地址，记录 mock 日志
 └─ 发请求接口       关闭
```

核心原则是**本地优先**：界面上的所有读写都只走本地服务和本地数据库，云端不在任何一次操作的路径上。有网和没网，用起来**完全一样**，区别只是右上角显示「已同步」还是「离线 · N 项待同步」。

**复用程度：** 桌面版里的本地服务就是现在这套 `lib/` 代码，通过启动参数切换成「桌面模式」。前端也基本是现在这套，只多了登录云端、同步状态、冲突处理这几块。真正新写的是：同步协议（云端加接口，本地加同步引擎）、Electron 外壳和打包。

## 4. 数据归属

| 数据 | 主存在哪 | 是否同步 | 说明 |
|---|---|---|---|
| 项目（名称、描述、变量、鉴权、脚本、mock 设置） | 本地 + 云端 | 双向 | |
| 目录、接口、示例、mock 期望 | 本地 + 云端 | 双向 | mock 相关的改动同步到云端后，云端的 mock 立刻生效 |
| 环境 | 本地 + 云端 | 双向 | 「当前环境」仍然只存在本机（和现在一样，是个人选择） |
| 用户、成员、角色 | 云端 | 只拉取 | 本地缓存一份，用来决定界面上哪些操作可用；成员管理只能联网操作 |
| 请求历史 | 本地 | **不同步** | 用户确认：只存本机 |
| Cookie | 本地 | 不同步 | 每台机器各自一份，和浏览器一样 |
| form-data 里上传的文件 | 本地 | 不同步 | 只存本机。其他人拉到这个接口时，显示「文件只在上传者的电脑上，请重新选择」 |
| Mock 日志 | 云端 | 联网时直接读云端 | 离线时显示「需要联网」 |

## 5. 同步协议

### 5.1 云端：版本号和变更流

- 每个需要同步的表（projects、folders、apis、examples、mock_expectations、environments）加两列：
  - `rev`：这一行在云端的版本号，每改一次加一；
  - `deleted`：删除标记。删除不真删，留一条「已删除」的记录，让其他设备知道。旧的删除标记定期清理，例如 90 天。
- 新表 `changes(seq, project_id, entity, entity_id)`：每次写入追加一条，`seq` 全局自增。
- `GET /sync/projects/:pid/changes?since=<seq>`：返回这个项目在 `since` 之后有变化的行（返回完整的行），以及最新的 `seq`。
  - 第一次同步时 `since=0`，相当于全量下载。
- `POST /sync/projects/:pid/push`：批量提交本地改动，格式是 `[{ entity, id, baseRev, data | deleted }]`。云端逐条处理，每条返回下面三种结果之一：
  - `ok`：附带新的 `rev`；
  - `conflict`：附带云端当前的那一行；
  - `forbidden`：没有权限。
- 权限照旧在云端检查：viewer 不能提交，editor 可以，项目成员管理只有 owner 能做。

### 5.2 本地：待同步队列和「基线」

- **主键在本地生成。** 现有的 `newId()` 是「时间戳 + 8 位随机串」，多台设备各自生成也不会撞。所以离线新建的接口直接就是正式 ID，不需要「临时 ID → 正式 ID」的替换。
- 本地每次写入时，同时在 `sync_outbox` 里给这一行打一个「待同步」标记。同一行改了多次，只算一条。
- 本地为每一行保存一份**基线**：上一次和云端对齐时云端的那一版，存在 `sync_base` 表里。用途：
  - 提交时带上 `baseRev`；
  - 发生冲突时做**按字段的三方合并**。
- 同步一轮的步骤：
  1. 先拉取：把云端的新变更写进本地。如果某一行本地没有改过，直接覆盖；如果本地也改过，交给 5.3 合并。
  2. 再推送：把待同步队列整批提交。
  3. 根据结果更新基线、清掉已经成功的标记。
- **什么时候同步：**
  - 启动时；
  - 本地有写入后约 2 秒（多次写入合并成一次）；
  - 联网状态下每 30 秒一次；
  - 网络从断开恢复时，立刻同步一次。
  - 判断有没有网：不依赖操作系统的联网状态，以能不能访问云端的 `/health` 为准。

### 5.3 冲突处理

同一行在本地和云端**都**改过的时候：

1. **按字段做三方合并**（基线 vs 本地 vs 云端）。两边改的是不同字段，就自动合并，不打扰用户。比如我改了地址，别人改了请求头，两边都保留。
2. 两边改了**同一个字段**，而且改得不一样：这一行进入「冲突」状态。界面上标红，打开时让用户选：
   - **用我的**：用本地的版本覆盖云端；
   - **用云端的**：放弃本地的修改；
   - **另存为副本**：只用于接口。把本地版本另存为「xxx（我的版本）」，原来那个接口采用云端的版本。
3. 一边删除、另一边修改：**修改优先**，把删除撤销，并给用户一条提示。
4. 目录树里的位置（父目录、排序）冲突：直接以后改的为准，不提示。拖动排序的冲突提示出来，只会让人困惑。

## 6. 登录和本地服务的安全

- **登录：** 桌面版第一次启动时填写云端地址，再用云端账号登录。云端签发一个**设备令牌**（新的 `device_tokens` 表，有效期 90 天，用一次续一次；用户可以在云端的个人设置里吊销）。
- 令牌用 Electron 的 `safeStorage` 加密保存（Mac 用钥匙串，Windows 用 DPAPI）。
- **离线启动：** 不验证令牌，直接用本地缓存的用户信息进入。下次连上云端时才验证；如果令牌已经失效，暂停同步，并提示重新登录。待同步的数据不会丢。
- **切换账号：** 每个「云端地址 + 账号」各用一个本地数据库文件，换账号不会看到别人的数据。
- **本地服务只给本程序用：**
  - 只监听 `127.0.0.1`，端口随机；
  - 每次启动生成一个随机口令，只有程序自己的窗口知道。每个请求都要带上这个口令，同时检查 `Host`。
  - 这样，其他网站或者本机上的其他程序，都没法借这个本地服务去访问你的内网。

## 7. 云端需要改的

- 加 `rev`、`deleted` 两列，加 `changes` 表和 `device_tokens` 表：**迁移 v6**。原先给 P10 预留的 v6 顺延成 v7。
- 加同步接口（5.1）和设备令牌的登录、吊销接口。
- 现有的增删改接口也要维护 `rev` 和 `changes`，这样从云端网页上做的修改也能同步下去。
- 关闭发请求的接口（`/send`、`/send/stream`、WebSocket 调试会话），返回「请使用桌面版」。
- 云端网页保留，用途变成：账号和成员管理、查看项目、查看 mock 日志。发送按钮隐藏，并提示去下载桌面版。云端网页上的「下载桌面版」入口链接到安装包。

## 8. 桌面版外壳和打包

- **Electron**：主进程启动本地服务，然后打开一个窗口加载本地页面。
- 本地数据库放在用户目录：
  - Mac：`~/Library/Application Support/apiloop/`
  - Windows：`%APPDATA%\apiloop\`
- 用 `electron-builder` 打包：
  - Mac：`.dmg`，同时出 Apple 芯片和 Intel 两个版本；
  - Windows：`.exe` 安装程序（NSIS），x64。
  - 不签名。
- 我们没有需要编译的原生依赖：SQLite 用 Node 自带的 `node:sqlite`，QuickJS 是 wasm，`ws` 是纯 JS。所以在一台 Mac 上就能同时打出 Windows 的安装包。
- 版本号和云端一致。桌面版连上云端时会检查云端的版本：如果太旧，同步协议可能不兼容，就提示去下载新的安装包。

## 10. 已确认的问题（2026-10-01）

1. **请求历史只存本机，不同步。** 用户的原话是「只有请求、环境、项目需要同步」，对应到数据上：
   - 「项目」包括项目本身和它的目录树；
   - 「请求」包括接口，以及挂在接口上的示例和 mock 期望（mock 在云端提供，这些必须同步上去）；
   - 「环境」就是环境。
   - 其余数据（历史、Cookie、上传的文件）都只存本机。
2. **云端网页保留编辑功能**，改动会同步到桌面版，只是不能发请求。
3. **不迁移现有数据**，现在的都是测试数据。D2 上线时可以直接清空云端的库。这也意味着**迁移 v6 不需要为旧数据补 `rev`**，可以直接按新的表结构建。

## 11. 风险

- **Electron 自带的 Node 能不能用 `node:sqlite`**：D0 第一件事就验证，有备选方案（见 D0）。
- **同步的正确性是整个方案里最难的部分**：会丢数据的 bug 代价最大。审阅时要专门推演这几类情况：
  - 断网期间两边都改了同一行；
  - 推送到一半网断了；
  - 同一个账号在两台设备上用；
  - 一边删除、一边修改。
- **不签名的安装包**：Mac 会拦一次，Windows 的 SmartScreen 也会提示。需要在使用说明里写清楚怎么打开。
